# Story 2.4: User accounts linked to staff and role assignment

Status: in-progress

## Story

As an administrator,
I want to create accounts for staff, assign roles, deactivate accounts and reset passwords,
So that every person works under their own account with exactly the access their job needs.

## Acceptance Criteria

1. **Given** `NguoiDung.CanBoId` (FK → `CanBo`, NULL only for the built-in admin) and `NguoiDungVaiTro` (composite PK)
   **When** the administrator creates an account with a unique `TenDangNhap`, an active staff member and one or more roles
   **Then** the account is saved with a temporary password and `PhaiDoiMatKhau = 1`

2. **Given** a staff member who already has an active account
   **When** a second active account is created for the same staff member
   **Then** it is rejected (one active account per person)

3. **Given** an existing account
   **When** the administrator deactivates it, unlocks it, resets its password or changes its roles
   **Then** the change takes effect at the user's next sign-in or permission check, and one audit row per action records who did it, when, and the before/after values (never the password or hash)

4. **Given** the last active account holding the `HT` administration permissions
   **When** someone tries to deactivate it or remove its admin role
   **Then** the action is refused so the system can never be left without an administrator

5. **Given** any user without `HT.Sua`
   **When** they call the account service directly
   **Then** an authorization error is raised and nothing is written

## Tasks / Subtasks

- [x] **T1. Persistence** (AC: 1, 2)
  - [x] Migration `AddNguoiDungCanBo`: `NguoiDung.CanBoId int NULL` FK → `CanBo` (`Restrict`). Add a filtered unique index `UX_NguoiDung_CanBoId_DangHoatDong` on `CanBoId` `WHERE DangHoatDong = 1 AND CanBoId IS NOT NULL`. That's the DB backstop for AC 2. The index alone allows several *inactive* accounts per person, which is what we want (history is kept).
  - [x] "NULL only for the built-in admin": add `CHECK (CanBoId IS NOT NULL OR TenDangNhap = 'admin')`, and enforce it in the service with a clear message. `NguoiDungVaiTro` already exists (2.3).
- [x] **T2. Application account service** (AC: 1–5)
  - [x] `HeThong/TaiKhoanService.cs` with `TaoAsync`, `CapNhatVaiTroAsync`, `NgungHoatDongAsync` / `KichHoatLaiAsync`, `MoKhoaAsync`, `DatLaiMatKhauAsync`, plus a list query (account, staff name, roles, active, locked, `PhaiDoiMatKhau`).
  - [x] **Every write method** starts with `await kiemTraQuyen.YeuCauAsync(MaQuyen.HT.Sua, ct)` (Story 2.3 T4), before any transaction (AC 5). Use `HT.Sua` for all of them, including create. The AC names one permission for the account service, and the admin role holds all of `HT` anyway.
  - [x] Create: `TenDangNhap` unique (pre-check + UQ backstop, Story 2.1 T4 pattern), 3–50 chars, letters/digits/`.`/`_`; an **active** staff member (from `LayCanBoDangCongTacAsync`); ≥ 1 role.
  - [x] **Temporary password**: generated by the service (12 chars, satisfies `ChinhSachMatKhau`, using `RandomNumberGenerator`, no look-alike characters such as `0/O/l/1`). It's returned to the presenter **once**, to show and copy, and never logged or stored in clear. Set `PhaiDoiMatKhau = 1`. Reset does the same and also clears the lock.
  - [x] Unlock: `GhiNhanDangNhapDung()`-like reset (`SoLanSai = 0`, `KhoaDen = null`). Deactivate: `DangHoatDong = 0`. Reactivate re-checks AC 2, because the staff member may have a newer active account.
  - [x] **Audit (AC 3).** `NguoiDung` is `IAuditable`, so field changes (`DangHoatDong`, `KhoaDen`, `SoLanSai`, `PhaiDoiMatKhau`, `CanBoId`) are logged automatically as `Sua`/`Them`, and `MatKhauHash` is excluded by `[KhongGhiNhatKy]`. Role changes touch only `NguoiDungVaiTro`, so log them explicitly via `IGhiNhatKy` (with the `duLieuCu` overload from 2.3): `Sua`, `TenBang = "NguoiDung"`, `BanGhiId` = user id, `{ "VaiTro": [sorted role codes] }` before/after. A password reset changes only the excluded hash plus `PhaiDoiMatKhau`, so its `Sua` row shows `PhaiDoiMatKhau false → true`. Also add an explicit `{ "SuKien": "DatLaiMatKhau" }` row so the action is unmistakable in the viewer.
  - [x] "Takes effect at next sign-in or permission check": nothing to push to other workstations. `IKiemTraQuyen` reads the DB on every write (2.3), and the menu is rebuilt at sign-in (2.5).
- [x] **T3. Last-administrator guard** (AC: 4)
  - [x] Define "administrator" as an **active account that holds `HT.Sua` through its roles**. That's the permission that manages accounts and roles, so without it nobody can repair access.
  - [x] Application `HeThong/KiemTraConQuanTri`: before deactivating an account, removing a role from it, or (Story 2.3's `VaiTroService.CapNhatQuyenAsync`) removing `HT.Sua` from a role, compute "active accounts with `HT.Sua` after the change". If none are left, refuse with "Không thể thực hiện: hệ thống phải còn ít nhất một tài khoản quản trị đang hoạt động".
  - [x] Run the check and the change in **one transaction at `Serializable`** isolation, so two admins demoting each other at the same moment can't both succeed. The rows involved are few, so the range locks are cheap.
  - [x] Also refuse a user deactivating **their own** account (a simple, friendly rule; signing yourself out of existence is never intended).
- [x] **T4. Current-user details** (needed by 2.5, 2.7 and Epic 4)
  - [x] Extend `ICurrentUser` with `int? CanBoId` and `string? HoTen` (the staff name, falling back to `TenDangNhap` for `admin`), loaded at sign-in. Epic 4 sets `CanBoLapId` from it, the lock screen (2.7) shows the name, and the duty-segregation policy (2.6) compares staff ids.
- [x] **T5. WinForms "Tài khoản" screen** (AC: 1–4)
  - [x] `HeThong/`: `ITaiKhoanView` + presenter + form. A grid (Tên đăng nhập, Cán bộ, Vai trò, Hoạt động, Bị khoá) with actions Thêm, Phân vai trò, Ngừng/Kích hoạt, Mở khoá, Đặt lại mật khẩu.
  - [x] The create dialog picks the staff member from **active staff without an active account**. Roles are a checked list.
  - [x] After create/reset, a small dialog shows the temporary password with a "Sao chép" (copy) button and the note "Người dùng phải đổi mật khẩu ở lần đăng nhập đầu tiên". Closing it discards the value.
  - [x] Destructive actions (deactivate, reset) ask for confirmation.
- [x] **T6. Tests** (AC: 1–5)
  - [x] Unit: temporary-password generator output always passes `ChinhSachMatKhau` (property-style loop over 1,000 samples); the guard's decision logic as a pure function (accounts × roles → is anyone left).
  - [x] Integration:
    - create → `PhaiDoiMatKhau = 1`, roles saved, `Them` audit row without a hash;
    - second active account for the same staff → rejected, and the filtered index also rejects a raw insert;
    - deactivate the only admin → refused; with two admins, one can be deactivated;
    - remove `HT.Sua` from `QUAN_TRI` while it's the only admin role → refused (2.3 path);

## Dev Notes

### Current codebase state (after 2.3)

- `CanBo` + `LayCanBoDangCongTacAsync` (2.1); lockout, `ChinhSachMatKhau`, `DoiMatKhauService` (2.2); `MaQuyen`, `VaiTro`, `NguoiDungVaiTro`, `IKiemTraQuyen`, `KhongCoQuyenException`, the `IGhiNhatKy` before/after overload (2.3).

### Design notes

- **One active account per person (NEN-09).** Duty segregation (2.6) compares people, not accounts. A second active account would let one person approve their own work, which is why 2.6 also checks `CanBoId`.
- **The built-in `admin` has no staff record.** Alignment A17: an account without `CanBoId` can't approve (enforced in 5.5) and has no `CanBoLapId` for documents (Epic 4). Encourage the unit to create a personal admin account for the IT officer and keep `admin` for emergencies. Put that in the install notes.
- Accounts are never hard-deleted. `NguoiDung` rows are referenced by `NguoiTaoId`/`NguoiSuaId` everywhere and by the audit log.

### Gotchas

- A `Serializable` transaction plus the audit interceptor: the interceptor joins the open transaction (Story 1.3), so start the transaction in the service before the first read.
- `ICurrentUser` is a singleton per process. Changing *another* user's roles never touches the local session. Changing *your own* roles takes effect at your next sign-in (menus) and immediately for writes (DB check).

### Out of scope

- The permission-driven menu (2.5). The approval rule itself (2.6). The DB-level DENY script (Epic 7).

### Debug Log References

1. **`Serializable` and the audit interceptor.** The guard must run inside the transaction the service opens before its first read, so the interceptor joins it (Story 1.3). `IAppDbContext` gained `BeginTransactionAsync(TransactionIsolation, ct)`; `TransactionIsolation.Serializable` maps to `IsolationLevel.Serializable` in `AppDbContext`. The merge had removed an incompatible overload; interface and implementation now agree.
2. **CHECK constraint vs. test fixtures.** The new `CK_User_OfficerId` rejected the accounts that `RoleServiceTests.CreateUserAsync` and the integration `SignInServiceTests.CreateAccountAsync` created without an officer. Both helpers now create an officer and link it — the rule working as intended.
3. **"Deactivate the only admin" is unreachable through `AccountService`.** The actor must itself hold `HT.Sua`, so after deactivating the target at least the actor remains; if the actor is the target, the self-deactivation rule fires first. The guard is therefore exercised directly (`Guard_DeactivatingTheOnlyAdministrator_IsRejected`) and through the role editor (`RoleService_RemovingAdminPermissionFromTheOnlyAdministratorRole_IsRejected`), each on a throw-away database where the seeded admin is deterministically the only administrator.
4. **`RoleService.UpdatePermissionsAsync` reordered.** The transaction now starts before the first read, as the story's gotcha requires; the catalogue pre-check stays outside it (in-memory only); the Story 2.3 TODO is gone.
5. **Demo accounts now link to staff.** `DemoDataSeeder` sets `OfficerId`, otherwise `--seed-demo` would violate the new CHECK.
6. **Rename migration test.** `RenameIdentifiersToEnglishMigrationTests` stops at the rename migration and then reads entities with the build's model; with `AddUserOfficer` in the chain the model has an `OfficerId` column the stopped schema lacks. The test now finishes the migration chain before the entity reads (raw row counts still prove the rename kept every row).
